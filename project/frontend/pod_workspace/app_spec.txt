  <section_0_system_invariants>
    <purpose>
      Define formal invariants, concurrency controls, and idempotency guarantees
      that apply across ALL modules. These rules are NOT optional — they are
      architectural constraints that every implementation must satisfy.
      Section 0 infrastructure (tables, functions, modules) must be deployed
      as the first migration of the hardening phase.
    </purpose>

    <system_invariants>
      INV-01: SINGLE REFUND PER ORDER
        Description: An order can have AT MOST one successful Stripe refund.
        Risk if violated: Customer refunded twice. Direct financial loss.
        Enforcement:
          - Column orders.stripe_refund_id VARCHAR(255) UNIQUE
          - Column orders.refunded_at TIMESTAMPTZ (NULL = not refunded)
          - PostgreSQL function issue_refund_atomic(order_id, stripe_refund_id, amount, reason)
            uses SELECT ... FOR UPDATE on the order row, checks refunded_at IS NULL,
            then atomically sets status='refunded' + refunded_at=now() + stripe_refund_id.
          - All refund paths (webhook cancel, cron 24h review, order:failed, admin manual)
            MUST call issue_refund_atomic(). If it returns FALSE, the Stripe refund must be reversed.
        Affected code:
          - frontend/src/app/api/webhooks/printify/route.ts (handleOrderCancelled, handleOrderFailed)
          - frontend/src/app/api/cron/retry-printify-orders/route.ts (requires_review 24h timeout)
          - admin order management (manual cancel+refund)

      INV-02: WEBHOOK EXACTLY-ONCE PROCESSING
        Description: A webhook event produces side effects at most once, regardless of redelivery.
        Risk if violated: Duplicate orders, duplicate refunds, duplicate status transitions.
        Enforcement:
          - Table processed_events (provider VARCHAR(50), event_id VARCHAR(255), event_type VARCHAR(100),
            processed_at TIMESTAMPTZ, UNIQUE(provider, event_id))
          - Pattern: INSERT INTO processed_events ... ON CONFLICT DO NOTHING RETURNING id.
            If RETURNING is empty → event already processed → return 200 OK without side effects.
          - For order-specific webhooks: additionally acquire pg_advisory_xact_lock(hashtext('order:' || order_id))
            to prevent two different event types racing on the same order.
        Affected code: All 4 webhook routes (Stripe, Printify, Telegram, WhatsApp).
        Event ID extraction:
          - Stripe: event.id (evt_xxxx)
          - Printify: request body .id or X-Printify-Event-Id header
          - Telegram: update_id
          - WhatsApp: messages[0].id

      INV-03: CRON MUTUAL EXCLUSION
        Description: A cron job instance must not overlap with another instance of itself.
        Risk if violated: Variant sync race conditions, duplicate emails, data corruption.
        Enforcement:
          - pg_try_advisory_xact_lock(hashtext('cron:' || cron_name)) at handler start.
            If returns FALSE → another instance running → return 200 OK (skip).
          - Record every execution in cron_runs table (cron_name, started_at, finished_at, status, duration_ms).
          - Rolling deploy safety: pg_advisory_lock is cluster-wide, so old+new instances sharing
            the same DB connection cannot overlap.
        Process death recovery: Advisory locks are released when the connection drops.
          cron_runs entry stays 'running' — ZombieReaper marks it 'failed' after 2x max_duration.
        Affected code: All 10 cron routes in frontend/src/app/api/cron/*/route.ts

      INV-04: VALID STATE TRANSITIONS ONLY
        Description: State changes must follow the defined transition matrix. All others are rejected.
        Risk if violated: Orders jump states (pending→delivered), products skip review.
        Enforcement:
          - All UPDATE ... SET status = :new_status queries include WHERE status = :expected_current_status.
          - If rows_affected = 0 → transition rejected → log to error_logs + alert admin.
          - StateTransitionValidator module validates (entity_type, current_state, target_state)
            against the hardcoded transition matrix before executing the UPDATE.
        Affected code: Every status update in webhooks, crons, admin actions, and API routes.

      INV-05: NO INDEFINITE ZOMBIE STATES
        Description: Every intermediate (non-terminal) state has a maximum TTL and automatic corrective action.
        Risk if violated: Orders stuck in 'paid' forever, products stuck in 'publishing', agent sessions never complete.
        Enforcement:
          - ZombieReaper cron runs every 15 minutes.
          - Queries each entity/state pair against the zombie_prevention table (see below).
          - Executes defined auto-action for expired states.
          - Sends escalation alert per defined tier.

      INV-06: ATOMIC FINANCIAL OPERATIONS
        Description: Operations involving money (credits, refunds, payments) must be atomic.
        Risk if violated: Partial credit deduction, lost refund record, inconsistent balance.
        Enforcement:
          - All financial mutations use SECURITY DEFINER PostgreSQL functions
            with explicit row-level locking (FOR UPDATE).
          - No application-level SELECT-then-UPDATE for money fields.
          - Functions: issue_refund_atomic(), consume_credit_atomic(), increment_usage_by(), add_credits().

      INV-07: AGENT SINGLETON EXECUTION
        Description: Only one instance of a given agent can be in 'running' state at any time.
        Risk if violated: Duplicate cataloging, conflicting marketing, budget overconsumption (2x).
        Enforcement:
          - Redis: SET NX podclaw:running:{agent_name} with TTL = 20min (max session time).
          - If SET NX fails → agent already running → return 409 Conflict.
          - On session completion/error → DEL podclaw:running:{agent_name}.
          - Fallback without Redis: check agent_sessions WHERE agent_name=:name AND status='running'.

      INV-08: AUDIT COMPLETENESS
        Description: Every admin mutation and every webhook event has an audit record.
        Risk if violated: No accountability, no debugging capability, GDPR compliance failure.
        Enforcement:
          - withAuth() middleware auto-logs to audit_log (synchronous INSERT before response).
          - Webhook handlers log to processed_events (request metadata) on receipt.
          - Agent actions logged to agent_events.

      INV-09: PII BOUNDARY
        Description: PII (email, name, address, phone) must never appear in logs, marketing content, or agent prompts.
        Risk if violated: GDPR violation, fines up to 4% annual revenue (EUR 20M minimum).
        Enforcement:
          - [DATA]...[/DATA] markers for all agent-processed user data.
          - structlog processors strip PII fields from log output.
          - marketing_content table has no PII columns — only product/brand data.

      INV-10: FAIL-CLOSED SECURITY
        Description: All security checks (auth, RLS, HMAC, CSRF) DENY on error, never ALLOW.
        Risk if violated: Unauthorized access during transient errors.
        Enforcement:
          - Every auth/verification function: catch block returns DENY/reject, never continues.
          - Pattern: if (error) return NextResponse.json({error}, {status: 401}), NOT if (error) log(error).
          - HMAC: if timingSafeEqual throws → REJECT webhook.
          - RLS: if Supabase RPC returns null → DENY request.
    </system_invariants>

      <retry_model>
        All retryable operations follow this formal model.

        Retry parameters per operation:
          | Operation                      | Max Attempts | Backoff        | Final Action                    |
          |--------------------------------|-------------|----------------|----------------------------------|
          | Printify order creation         | 3           | 2s, 4s, 8s    | Auto-refund via RefundGuard      |
          | Printify order submission       | 3           | 2s, 4s, 8s    | Mark requires_review             |
          | Printify API call (read)        | 3           | 2s, 4s, 8s    | Return cached/stale data         |
          | Printify API call (write)       | 3           | 2s, 4s, 8s    | Circuit break 60s + alert        |
          | Stripe API call                 | 3           | 1s, 2s, 4s    | Log + alert admin                |
          | fal.ai API call                 | 2           | 3s, 6s        | Return error to user             |
          | Email delivery (Resend)         | 3           | 5s, 30s, 5min | Log + retry next drip cycle      |
          | Agent session                   | 2           | 60s + jitter   | Mark failed_final + alert        |

        Backoff formula: delay = base_delay * (2 ^ attempt) + random(0, base_delay * 0.5)
        Jitter prevents thundering herd on recovery after outage.

        After final attempt failure:
          - Financial operations → auto-refund if applicable, alert L2
          - Non-financial → log to error_logs with severity='critical', alert L1
          - Agent sessions → mark failed_final, do NOT retry infinitely

        Dead-letter handling:
          Operations failing all retries logged to error_logs:
            {severity: 'critical', context: {operation, attempts, last_error, entity_id, timestamp}}
          EscalationManager sends L2 alert (Telegram + email) within 2 minutes.
      </retry_model>

      <refund_atomic_model>
        MECHANISM: issue_refund_atomic() PostgreSQL function + UNIQUE constraint

        New columns on orders table (migration YYYYMMDD_system_invariants.sql):
          ALTER TABLE orders ADD COLUMN IF NOT EXISTS stripe_refund_id VARCHAR(255) UNIQUE;
          ALTER TABLE orders ADD COLUMN IF NOT EXISTS refunded_at TIMESTAMPTZ;
          ALTER TABLE orders ADD COLUMN IF NOT EXISTS refund_amount_cents INTEGER;
          ALTER TABLE orders ADD COLUMN IF NOT EXISTS refund_reason VARCHAR(100);
          ALTER TABLE orders ADD COLUMN IF NOT EXISTS retry_count INTEGER DEFAULT 0;

        New function (same migration):
          CREATE OR REPLACE FUNCTION issue_refund_atomic(
            p_order_id UUID,
            p_stripe_refund_id VARCHAR,
            p_amount_cents INTEGER,
            p_reason VARCHAR
          ) RETURNS BOOLEAN AS $$
          DECLARE
            v_current_status VARCHAR;
            v_already_refunded BOOLEAN;
          BEGIN
            SELECT status, (refunded_at IS NOT NULL)
            INTO v_current_status, v_already_refunded
            FROM orders WHERE id = p_order_id FOR UPDATE;

            IF v_already_refunded THEN RETURN FALSE; END IF;
            IF v_current_status NOT IN ('cancelled','requires_review','paid') THEN RETURN FALSE; END IF;

            UPDATE orders SET
              status = 'refunded',
              stripe_refund_id = p_stripe_refund_id,
              refunded_at = now(),
              refund_amount_cents = p_amount_cents,
              refund_reason = p_reason
            WHERE id = p_order_id;
            RETURN TRUE;
          END;
          $$ LANGUAGE plpgsql SECURITY DEFINER;

        Application usage (ALL refund paths):
          1. const refund = await stripe.refunds.create({payment_intent, amount});
          2. const success = await supabase.rpc('issue_refund_atomic', {
               p_order_id: orderId,
               p_stripe_refund_id: refund.id,
               p_amount_cents: amount,
               p_reason: reason
             });
          3. If success=false → Stripe refund was created but DB says already refunded
             → Cancel the Stripe refund: await stripe.refunds.cancel(refund.id)
          4. If success=true → send notification + log to audit_log

        This guarantees: webhook cancel + cron 24h + order:failed firing simultaneously →
        only ONE succeeds at DB level. Others get FALSE and handle gracefully.
      </refund_atomic_model>

    <zombie_prevention>

      ZombieReaper cron runs every 15 minutes and enforces these limits.

      | Entity  | State              | Max TTL  | Detection                                              | Auto-Action                           | Escalation |

      | Order   | paid               | 30min    | status='paid' AND retry_count &lt; 3 AND updated_at &lt; now()-interval '30min' | Retry Printify submission | L1 |
      | Order   | paid (exhausted)   | 2h       | status='paid' AND retry_count >= 3                     | Auto-refund via issue_refund_atomic() | L2         |

      | Order   | shipped            | 30d      | status='shipped' AND updated_at &lt; now()-interval '30d' | Auto-confirm delivery                | L1         |

        - Resolution cached in Redis for 5min, falls back to DB query

      STRIPE MODEL: Stripe Connect (Standard)
        - Platform account collects platform fees
        - Each tenant has own Stripe connected account
        - Direct charges with application_fee_amount

      AGENT ISOLATION: Configuration-based (NOT separate processes)
        - Single PodClaw instance serves all tenants
        - tenant_configs table replaces global config.py values
        - Agent sessions include tenant_id, RLS prevents cross-tenant queries
        - Budget limits per-tenant (not global)

  <reliability_rules>
    Cross-cutting reliability rules for all 15 modules (0-14).
    Each rule references its enforcement mechanism from Section 0.

    RULE 1 — FAIL-CLOSED (INV-10)
      Enforced by: Application-level pattern (every auth/verify function)
      Specification: Security checks (auth, RLS, HMAC, CSRF) MUST deny on error, never allow.
        - if (error) → return DENY/reject, NOT log-and-continue
        - Supabase RPC returns null → DENY request (not "assume allowed")
        - HMAC timingSafeEqual throws → REJECT webhook (not "skip verification")
        - RLS query returns zero rows → DENY access (not "return empty array")
      Monitoring: EscalationManager L2 alert on any auth bypass detection

    RULE 2 — EXACTLY-ONCE PROCESSING (INV-02)
      Enforced by: WebhookProcessor module (Module 2)
      Specification: All webhook handlers and cron jobs produce side effects at most once.
        - Webhooks: INSERT INTO processed_events ON CONFLICT DO NOTHING
        - Crons: pg_try_advisory_xact_lock via CronLockManager (Module 1)
        - Order mutations: additional pg_advisory_xact_lock(hashtext('order:' || order_id))
        - DB constraints: orders.stripe_session_id UNIQUE, orders.stripe_refund_id UNIQUE
      Monitoring: processed_events duplicates counted in DivergenceDetector (Module 8)

    RULE 3 — GRACEFUL DEGRADATION
      Enforced by: Application startup + runtime checks
      Specification: Redis is OPTIONAL everywhere — services MUST start and function without it.
        - Rate limiting: falls back to in-memory Map with 5min TTL
        - Agent singleton (INV-07): falls back to agent_sessions DB query
        - Caching: degrades to no-cache (direct DB query)
        - Startup: NEVER block waiting for Redis connection
      Monitoring: Redis connection status exposed in /api/health deep check

    RULE 4 — ATOMIC FINANCIALS (INV-01, INV-06)
      Enforced by: RefundGuard module (Module 3) + PostgreSQL SECURITY DEFINER functions
      Specification: Operations involving money use atomic DB functions with row-level locking.
        - Refunds: issue_refund_atomic() — SELECT FOR UPDATE → check → UPDATE
        - Credits: consume_credit_atomic(), add_credits() — same pattern
        - Usage: increment_usage_by() — atomic increment
        - PROHIBITED: Application-level SELECT-then-UPDATE for ANY money field
      Monitoring: EscalationManager L2 alert on any refund function returning FALSE

    RULE 5 — EXPONENTIAL BACKOFF WITH JITTER
      Enforced by: RetryManager module (Module 6)
      Specification: All external API calls have retry with backoff on 429/5xx.
        - Formula: delay = base_delay * (2^attempt) + random(0, base_delay * 0.5)
        - Printify: 3 attempts, 2s/4s/8s + jitter. Respect Retry-After header on 429.
        - Stripe: 3 attempts, 1s/2s/4s + jitter.
        - fal.ai: 2 attempts, 3s/6s + jitter.
        - Resend email: 3 attempts, 5s/30s/5min.
        - After final failure: dead-letter to error_logs + EscalationManager alert
      Monitoring: RetryManager logs attempt counts to cron_runs.rows_affected or error_logs

    RULE 6 — BUDGET DEFENSE (dual-layer, NEVER single-layer)
      Enforced by: PodClaw config.py + Claude Agent SDK
      Specification: PodClaw agents have TWO independent budget protections:
        - Layer 1: SDK max_budget_usd per session (hard stop by SDK itself)
        - Layer 2: cost_guard_hook daily EUR limit (cumulative across sessions)
        - Thresholds: 80% warning (L1 alert) → 90% critical (L1 alert) → 100% hard stop
        - PROHIBITED: Disabling either layer "because the other exists"
      Monitoring: Budget usage exposed via GET /metrics (Prometheus format)

    RULE 7 — PII BOUNDARIES (INV-09)
      Enforced by: PodClaw security hook + structlog processors
      Specification: PII (email, name, address, phone) NEVER appears in:
        - Agent prompts or marketing content (use [DATA]...[/DATA] markers)
        - Log output (structlog processors strip PII fields)
        - Error messages returned to clients (generic errors only)
        - marketing_content table (no PII columns exist by design)
      Monitoring: Compliance audit cron scans agent_events for PII patterns weekly

    RULE 8 — COMPLETE AUDIT TRAIL (INV-08)
      Enforced by: withAuth() middleware + WebhookProcessor + agent_events
      Specification: Every state-changing operation has an immutable audit record.
        - Admin mutations: withAuth() auto-inserts to audit_log BEFORE response
        - Webhook events: WebhookProcessor logs to processed_events on receipt
        - Agent actions: agent_events table (action, result, cost, duration)
        - Product deletions: audit_log with actor, reason, timestamp, recoverable=true
      Monitoring: DivergenceDetector (Module 8) flags orders without audit trail

    RULE 9 — VALID STATE TRANSITIONS ONLY (INV-04)
      Enforced by: StateTransitionValidator module (Module 4)
      Specification: State changes follow the transition matrices defined in <state_machines>.
        - Every UPDATE SET status=:new includes WHERE status=:expected_current
        - rows_affected=0 → transition rejected → log to error_logs + L1 alert
        - StateTransitionValidator.transition() validates BEFORE executing the UPDATE
        - PROHIBITED: Direct UPDATE without checking current state
      Monitoring: Rejected transitions counted and exposed in Prometheus metrics

    RULE 10 — NO ZOMBIE STATES (INV-05)
      Enforced by: ZombieReaper module (Module 5)
      Specification: Every intermediate state has a max TTL (defined in zombie_prevention table).
        - ZombieReaper cron runs every 15min
        - Executes auto-action for expired states (retry, refund, alert, expire)
        - Sends escalation per defined tier (L1/L2/L3)
        - If auto-action fails → escalate to next tier
      Monitoring: ZombieReaper execution results logged to cron_runs
  </reliability_rules>
