  <overview>
    Build a 100% AI-managed Print-on-Demand platform where an autonomous AI agent harness
    ("PodClaw" — built on Claude Agent SDK) IS the store. PodClaw researches trends,
    generates designs, creates products, sets prices, handles customer interactions, manages
    finances, and optimizes the catalog — all autonomously, 24/7.

    The PRIMARY customer interface is a conversational AI storefront: a three-panel layout
    (store navigation sidebar + generative chat + product detail panel) where customers
    discover, customize, and purchase products through natural language in 3 languages.
    The chat is not a feature OF a traditional store — it IS the store. PodClaw's intelligence
    powers both the autonomous backend operations AND the real-time customer-facing chat.

    Traditional pages (/shop, /products/:id) exist as secondary SEO/fallback routes for
    search engine indexing and direct-link access, not as the primary shopping experience.

    The frontend is a Next.js 16 App Router PWA where the landing page (/[locale]/) IS the
    three-panel conversational storefront. Artifacts render INLINE in chat messages (product
    grids, design previews with action buttons) and expand to the right detail panel on click.
    The backend uses Next.js 16 API routes (app/api/) for Printify/Stripe webhooks, order
    processing, the RAG retrieval pipeline, A/B testing, and the PodClaw agent API. No separate Express server needed.
    A Python analytics layer runs scheduled cron jobs for RFM segmentation, demand forecasting,
    pricing optimization, and trend detection — feeding pre-calculated data to PodClaw.
    Data lives in Supabase (PostgreSQL + pgvector, 24 tables). Redis handles sessions, caching,
    and semantic cache for the RAG pipeline.
  </overview>

      <ai_sdk_integration description="AI SDK 6 (v5.x) technical patterns for storefront implementation">
        FRONTEND (React hooks):
        - useChat() from 'ai/react' with DefaultChatTransport — NOT raw fetch
          * transport: new DefaultChatTransport({ api: '/api/chat' })
          * sendMessage(text) replaces handleSubmit() — call directly, no form event needed
          * messages typed as UIMessage[] (NOT Message[]) — each has .parts array
          * message.parts[].type: 'text' | 'reasoning' | 'tool-invocation' | 'tool-result' | 'source' | 'step-start' | 'file'
          * Tool invocation states: 'partial-call' → 'call' → 'result'
          * DataPart for custom streaming: dataStream.writeData({ type, payload }) → useChat().data
        - message.parts rendering pattern:
          message.parts.map(part => {
            if (part.type === 'text') return <MarkdownRenderer text={part.text} />
            if (part.type === 'tool-invocation') {
              const Component = artifactRegistry[part.toolInvocation.toolName]
              if (part.toolInvocation.state === 'call') return <Component.Skeleton />
              if (part.toolInvocation.state === 'result') return <Component data={part.toolInvocation.result} />
            }
          })

        BACKEND (Route handler /api/chat):
        - streamText() from 'ai' with tool() definitions
        - convertToModelMessages(messages) — NOT convertToCoreMessages (renamed in v5.x)
        - return result.toUIMessageStreamResponse() — NOT toDataStreamResponse (renamed in v5.x)
        - ToolLoopAgent pattern: maxSteps: 5 (or stopWhen: stepCountIs(5))
        - needsApproval: true on create_checkout and request_return tools
        - prepareStep for injecting context per step (user profile, cart state)
        - onStepFinish for logging/analytics

        APPROVAL FLOW:
        - Tool with needsApproval=true → response includes approval-required state
        - Frontend renders ApprovalCardArtifact with Approve/Reject buttons
        - User clicks → addToolApprovalResponse(toolCallId, approved)
        - Check lastAssistantMessageIsCompleteWithApprovalResponses before re-sending
        - Re-send messages to continue the tool loop

        DATAPART STREAMING (sidebar updates):
        - Backend: dataStream.writeData({ type: 'sidebar-recommendations', products: [...] })
        - Backend: dataStream.writeData({ type: 'sidebar-trending', products: [...] })
        - Frontend: useChat().data listener updates sidebar state contextually
        - Recommendations adapt to conversation context in real-time
      </ai_sdk_integration>

    <phase_15 name="Security Hardening + Tiered Usage Limits">
      <!-- Auth Guard Module (src/lib/auth-guard.ts) -->
      - Create reusable auth-guard.ts module eliminating cookie-parsing duplication across 8+ API routes
      - Exports: getAuthUser(req), requireAuth(req), requireAdmin(req), handleAuthError(error), getClientIP(req), AuthError class
      - getAuthUser reads sb-access-token cookie, verifies with supabase.auth.getUser(), fetches role + tier from users table
      - requireAuth throws 401 if no valid session; requireAdmin throws 403 if role !== 'admin'
      - getClientIP resolves cf-connecting-ip > x-real-ip > x-forwarded-for

      <!-- Usage Limiter Module (src/lib/usage-limiter.ts) -->
      - Create usage-limiter.ts with USAGE_TIERS constant, checkAndIncrementUsage(), usageHeaders()
      - USAGE_TIERS defines limits per tier (anonymous/free/premium) per action (chat, design:generate, design:mockup, design:save)
      - Tier limits: anonymous=10 chat/day + BLOCKED design; free=50 chat + 3 generate + 5 mockup + 20 save; premium=500/30/50/unlimited
      - Redis primary storage: key usage:{id}:{action}:{YYYY-MM-DD} with INCR + EXPIRE (TTL until midnight UTC)
      - Supabase fallback via RPC increment_usage when Redis unavailable
      - Fail-open: if both Redis and Supabase down, allow request with warning log (do not block paying users)
      - Blocked actions (limit=0) denied immediately without touching storage
      - Response includes X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset headers

      <!-- DB Migration (supabase/migrations/20260214180000_user_usage_tracking.sql) -->
      - ALTER TABLE users ADD COLUMN tier VARCHAR(20) DEFAULT 'free' CHECK (tier IN ('free', 'premium'))
      - CREATE TABLE user_usage (id, identifier, action, period, count, created_at, updated_at) with UNIQUE(identifier, action, period)
      - CREATE FUNCTION increment_usage(p_identifier, p_action, p_period, p_limit) RETURNS JSONB (atomic upsert)
      - ALTER TABLE designs ADD COLUMN moderated_by UUID REFERENCES users(id), moderated_at TIMESTAMPTZ
      - RLS on user_usage: only service_role access

      <!-- Critical Vulnerability Fixes -->
      - POST /api/admin/migrate: add requireAdmin + block in production (NODE_ENV=production → 403) + audit log
      - POST /api/admin/designs/moderate: replace TODO comment with requireAdmin, add moderated_by + moderated_at
      - GET /api/orders/[id]: add requireAuth + ownership check (return 404 not 403 to prevent ID enumeration)
      - GET /api/orders: fix cookie name bug (sb-auth-token → sb-access-token), replace manual parsing with requireAuth
      - GET /api/wishlist: fix cookie name bug (sb-session → sb-access-token), replace with getAuthUser

      <!-- AI Endpoint Usage Limits -->
      - POST /api/designs/generate: requireAuth (anonymous blocked) + checkAndIncrementUsage('design:generate')
      - POST /api/designs/mockup: requireAuth (anonymous blocked) + checkAndIncrementUsage('design:mockup')
      - POST /api/chat: remove edge runtime (ioredis needs Node.js), use getAuthUser, add per-tier daily limits
      - POST /api/chat generate_design tool: verify auth + separate design quota check inside tool execution
      - 429 responses include upgradeMessage with tier upgrade CTA
      - Keep existing chatLimiter in-memory as burst protection (30/min), complementing daily tier limits

      <!-- Architecture Decisions -->
      - Fail-open for usage limits, fail-closed for auth (outage allows usage but blocks unverified identity)
      - 404 instead of 403 for ownership failures (prevents order ID enumeration)
      - Edge runtime removed from chat (ioredis requires TCP sockets, chat already does 5+ DB queries)
      - Tier limits as code constants not DB (intentional — limit changes require deploy)
      - Redis TTL for daily reset (counter reset on Redis restart is acceptable soft quota)
    </phase_15>
